# SDK 개선 분석

분석일: 2026-09-17. 대상: 현재 저장소의 코어, Android 런타임, MediaPipe 어댑터, 학습·평가 코드와 샘플 앱.

이 문서는 개선 전 코드의 분석 기록입니다. 이후 카운팅 회귀 수정, 지정 모드, 완료 이벤트·운동별 설정, 부분 관절 추적, 클래스 선택·잔차 TCN 실험, 평가 및 모델 asset 로딩을 구현했습니다. 현재 사용법은 [README](../README.md), 실행 검증은 [검증 기록](validation.md)을 참고하세요. 단계 예측 모델·ST-GCN·실제 데이터 학습은 후속 실험 항목입니다.

**판단**

Android용 온디바이스 SDK의 기반은 마련되어 있다. 특징 추출, 시계열 처리, 분류, 단계 추적, 모델 로딩이 분리되어 있고, Kotlin/Python 특징 일치 검사와 모델 체크섬·텐서 검사가 있다. 참가자별 데이터 분리와 시퀀스 평가도 유지할 가치가 있다.

현재 가장 먼저 개선할 부분은 완료 이벤트와 운동 분류의 결합, 연속 반복 처리, 관절 가림 처리다. 이 문제들은 더 좋은 분류 모델만 추가해도 남는다. 실제 데이터가 없는 상태에서 특정 신경망으로 교체하면 정확도가 높아진다고 단정할 근거는 없다.

아래의 재현 결과는 합성 좌표·제어된 분류 출력을 사용한 로직 검사다. 실제 사람의 인식 정확도 측정과 구분해야 한다.

| 우선순위 | 확인한 동작 | 영향 | 변경 방향 |
| --- | --- | --- | --- |
| P0 | 기하학적 완료 후 `other`가 확정되면 `pending.clear()` | 이미 수행한 반복 누락 | 반복 중 축적한 분류 근거로 완료 이벤트 판정 |
| P0 | 완료 확인 대기 중 한 번의 좌표 불량으로 후보 삭제 | 짧은 가림에도 횟수 누락 | 관측된 완료와 진행 중 반복의 유실 정책 분리 |
| P0 | 완료 후 준비 자세 안정 시간을 다시 요구 | 연속 동작의 다음 반복 누락 | 이미 관측한 상단 안정 상태를 다음 반복 준비에 재사용 |
| P1 | 손목을 포함한 필수 12관절 중 하나만 가려져도 모든 특징 무효 | 하체 운동에서도 손목 가림이 전체 추적 중단 | 운동별 필수 관절, 부분 유효성, 좌우 관측 신뢰도 도입 |

**1-1. 완료 시점의 분류 결과와 반복 자체를 분리**

[MotionEngine.kt](../core/src/commonMain/kotlin/io/motionengine/core/MotionEngine.kt)의 완료 후보는 기본 500ms 뒤에 집계되며, 그 시점의 확정 운동 ID와 일치해야 한다. 그런데 [data.py](../training/motion_training/data.py)의 정답은 반복 종료 이후 즉시 `other`가 된다. 따라서 동작 종료를 정확히 분류하는 모델일수록 완료 후보를 확인하기 전에 제거할 수 있는 구조다.

기존 테스트의 합성 스쿼트 좌표를 사용하고, 기본 `minValidSteps=15`, `stableDurationMs=200`, `completionDelayMs=500`을 적용한 재현:

- 계속 `squat`로 분류: 기하학적 완료 900ms, 이벤트 1400ms, 1회.
- 1000ms부터 `other`로 분류: 0회.
- 계속 `squat`로 분류하되 1000ms에만 `processMissing()`: 0회.

권장 설계는 반복별 후보 객체를 두는 것이다. 후보는 운동 ID, 시작·기하학적 종료 시각, 분류 점수의 시간적 근거, 관측 품질, 취소 사유를 가진다. 현재 프레임이 대기 자세라는 사실과 방금 완료한 반복의 유효성을 별도로 판단한다.

완료 후보를 무조건 유지하는 방식도 적절하지 않다. 스쿼트 뒤 도약을 관측한 경우, 중요한 완료 구간이 가려진 경우, 사람 교체나 장시간 유실이 있는 경우를 구분해야 한다. 점프 여부를 판단할 추가 관측이 부족하면 확인을 유예하거나 불확실로 종료한다. `completionDelayMs=0`만 적용하면 기존 스쿼트/점프스쿼트 중복 방지 목적이 깨질 수 있다.

`repId`, `startedAtMs`, `endedAtMs`, `emittedAtMs`를 가진 완료 이벤트를 현재 자세 결과와 분리하면, 직전 반복 확인 중 다음 반복이 시작돼도 UI와 평가기가 두 동작을 혼동하지 않는다. 운동 ID별 단일 후보 맵도 필요에 따라 반복별 큐로 바꾼다.

**1-2. 연속 반복에서 준비 자세를 이중으로 요구**

[Progress.kt](../core/src/commonMain/kotlin/io/motionengine/core/Progress.kt)는 상승 끝에서 `stable(ready)`로 완료를 판정한 뒤 `complete` 상태에서 다시 같은 준비 자세의 안정 시간을 요구한다.

100ms 간격의 특징 입력으로 다음을 재현했다. 두 사이클 모두 바닥 각도에 도달하고 상단 자세를 유지한다.

- 첫 반복 완료 직후 다음 하강 시작: 두 사이클 중 1회.
- 첫 완료 뒤 상단 자세를 추가 300ms 유지: 2회.

초기 세션의 준비 자세 확인과 반복 사이의 재시작 조건을 분리한다. 완료를 성립시킨 상단 안정 관측을 다음 반복 준비에도 활용하고, 다음 하강의 방향·변위와 최소 지속 시간으로 새 반복을 연다. 동일 자세 유지로 이벤트가 중복되지 않는 성질은 보존한다.

**1-3. 관절 품질을 운동별로 처리**

[Features.kt](../core/src/commonMain/kotlin/io/motionengine/core/Features.kt)는 양쪽 어깨·팔꿈치·손목·골반·무릎·발목의 영상/world visibility를 모두 요구한다. 스쿼트 좌표에서 손목 하나의 visibility만 0.4로 바꾸면 특징 전체가 `null`이 됨을 재현했다. 카운터의 무릎·팔꿈치 각도는 좌우 단순 평균이다.

권장 변경:

- 스쿼트와 푸쉬업의 필수 관절 집합을 분리한다.
- 관절별 또는 특징별 유효 마스크를 추가한다. 전체 프레임의 0/1 마스크만으로는 부분 가림을 표현할 수 없다.
- 좌우 신뢰도에 따른 가중치 또는 관측 가능한 한쪽을 사용하되, 반복 도중 측면 전환에 따른 각도 점프를 억제한다.
- 짧은 유실의 복구는 시간 제한과 불확실성 표시를 두며, 관측하지 않은 바닥·착지 단계를 추정만으로 완료 처리하지 않는다.
- 실시간 평활화와 이상치 억제를 적용하고, 시간에 따른 지연 증가를 함께 평가한다. 미래 프레임을 쓰는 평활화는 온라인 경로에 넣지 않는다.

특징 의미·마스크 변경 시 Kotlin과 Python을 함께 수정하고 `featureVersion`을 올린 뒤 재학습해야 한다. 현재 모델에 새 특징을 그대로 넣을 수 없다.

**2. 카운팅 구조의 권장 확장**

운동 자동 인식과 사용자가 선택한 운동 모드를 함께 지원하는 것이 좋다. 아래 이름은 제안이며 현재 API에 존재하지 않는다.

- `AUTO`: 운동 종류를 추론하고 운동 간 전환을 처리한다.
- `GUIDED(squat)`: 사용자가 선택한 스쿼트 추적기를 중심으로 동작한다. 잘못된 운동·가림 검사는 별도로 둔다.

현재 `MotionEngine`은 분류기를 필수로 받고 카운팅 설정도 분류기의 manifest에서 가져온다. 규칙만 사용하는 모드를 추가하려면 `TrackingConfig`와 모델 설정을 분리해야 한다. 단순히 항상 스쿼트를 반환하는 가짜 분류기를 제품 API로 제공하는 방식은 피한다.

현재 단일 `CycleTracker`의 운동별 분기를 `SquatTracker`, `PushUpTracker`, `JumpSquatTracker`, `BurpeeTracker`로 분리하고, 시간·안정성·반복 이벤트 처리는 공통 구성요소로 추출한다. 운동별 설정을 제공하면 스쿼트와 버피에 같은 지연·유실·안정 기준을 강제하지 않아도 된다.

개인화는 준비 자세의 관절 각도·몸통 스케일·카메라 조건을 보정하는 수준부터 시작한다. 사용자가 한 번 얕게 앉았다는 이유로 이를 정상 스쿼트 깊이로 자동 설정하지 않는다. 반복 집계, 부분 동작, 자세 평가의 제품 의미를 먼저 구분한다.

**3. 새 모델 후보와 도입 순서**

| 후보 | 용도 | 이 SDK에서의 판단 |
| --- | --- | --- |
| 현재 TCN 개선 | 운동 종류 분류 | 실제 데이터 기준 모델로 먼저 유지. 구조·학습 변경을 하나씩 비교 |
| 운동 종류 + 단계/경계 예측 TCN | 내려감·바닥·올라감·종료의 학습 | 가장 먼저 검토할 모델 확장. 단계 추적 규칙과 결합 |
| 소형 GRU | 과거 상태를 유지하는 시계열 추론 | 상태 초기화·직렬 처리·변환 호환성을 포함해 TCN과 비교할 대안 |
| 소형 ST-GCN 계열 | 관절 연결과 시간 변화를 함께 학습 | 운동 종류 증가 또는 수작업 특징 한계가 확인될 때 비교 |
| RepNet / TransRAC 계열 | 영상의 반복 주기·밀도 기반 카운팅 | 연구 비교 대상으로 활용. 현재 입력·출력 규격의 직접 대체품은 아님 |
| MediaPipe Full / Heavy | 관절 추출 품질 변화 | Lite와 같은 실기기·촬영 조건에서 비교할 후보 |

이 표의 우선순위는 현재 코드 구조에 근거한 설계 판단이다. 모델 간 정확도·속도 우위를 실측한 결과가 아니다.

**3-1. 현재 TCN의 개선**

[train.py](../training/motion_training/train.py)는 커널 크기 3, dilation 1·2·4·8·16·32의 인과적 Conv1D 6층과 마지막 시점의 5종 softmax 출력으로 구성되어 있다.

입력 창은 180시점, 6초지만 마지막 출력이 직접 참조하는 특징의 범위는 `1 + 2 × (1+2+4+8+16+32) = 127`시점, 약 4.2초다. 6초 전체를 활용한다고 해석하면 안 된다. 느린 동작에서 긴 문맥이 필요한지는 데이터로 확인하고 dilation·블록 구성을 조정한다.

우선 실험할 변경은 residual block, 적절한 정규화·dropout, 클래스/참가자 균형 샘플링, 시간 속도 변형과 좌표 잡음·유실 증강이다. 증강은 실제 관절 좌표의 기하와 영상/world 좌표의 일관성을 보존해야 하며, 변형 후 특징과 속도를 다시 계산해야 한다.

평가 기준은 프레임 분류 F1만으로 제한하지 않는다. 분류 임계값·연속 확정 시간·완료 지연을 검증 세션의 반복 누락, 오검출, 확인 지연을 기준으로 함께 선택한다. 최종 시험 참가자는 이 조정에 사용하지 않는다.

**3-2. 단계까지 학습하는 모델**

이미 annotation에 `start`, `bottom`, `end` 등의 경계가 있으므로 운동 종류 외에 현재 단계나 종료 경계를 학습하는 출력으로 확장할 수 있다. 단계 구간에 모호한 프레임이 있으면 강제 라벨보다 제외 마스크나 검토 구간을 둔다.

권장 흐름은 `특징 → 운동/단계 점수 → 허용된 단계 전이 검사 → 반복 이벤트`다. 단계 점수가 한 프레임 튄 것만으로 횟수를 올리지 않고, 단계 순서·관측 품질·최소 지속 시간을 함께 확인한다. 실시간 모델은 미래 관측 없이 동작하도록 학습·평가해야 한다.

TCN의 시간적 동작 분할 적용은 [Temporal Convolutional Networks for Action Segmentation and Detection](https://arxiv.org/abs/1611.05267)을 참고할 수 있다. 논문의 성능이 이 SDK의 운동 데이터에서도 재현된다는 뜻은 아니다.

**3-3. 관절 그래프 모델과 범용 반복 모델**

[ST-GCN](https://arxiv.org/abs/1801.07455)은 골격의 공간 연결과 시간 변화를 학습하는 모델이다. 현재 32개 수작업 특징으로 구분하기 어려운 운동을 추가할 때 비교할 가치가 있다. MediaPipe 관절에 맞는 그래프, 결측 마스크, 인과적 시간 처리, Android 변환·지연 검증이 필요하다. 다른 관절 규격으로 사전 학습된 가중치를 그대로 사용할 수 있다고 가정하지 않는다.

[RepNet](https://openaccess.thecvf.com/content_CVPR_2020/html/Dwibedi_Counting_Out_Time_Class_Agnostic_Video_Repetition_Counting_in_the_CVPR_2020_paper.html)은 영상의 시간적 자기 유사성으로 반복 주기를 예측한다. [TransRAC](https://openaccess.thecvf.com/content/CVPR2022/html/Hu_TransRAC_Encoding_Multi-Scale_Temporal_Correlation_With_Transformers_for_Repetitive_Action_CVPR_2022_paper.html)은 여러 시간 규모의 상관관계와 밀도 회귀를 이용한다. 두 연구의 방식은 다양한 반복의 비교 기준으로 유용하지만, 현재 좌표 입력·프레임별 완료 이벤트·모바일 실행 요구와의 간극을 별도로 해결해야 한다. 중단·부분 동작을 무엇으로 셀지도 따로 정의해야 한다.

[MediaPipe 공식 문서](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker)는 Lite·Full·Heavy 모델과 33개 관절, 영상/world 좌표 출력을 제공한다. 이 모델 선택을 실험할 때는 관절 품질뿐 아니라 카메라부터 결과 표시까지의 처리 지연과 발열도 비교한다. 현재 수집 앱은 가져온 파일을 lite 이름으로 저장하므로, 실험용 메타데이터에는 실제 모델 종류·버전·해시를 기록하도록 개선한다.

**4. 모델을 추가하려면 함께 바꿔야 하는 규격**

현재 확장 지점인 `MotionClassifier`와 `ExerciseDefinition`은 유지할 가치가 있다. 다만 자유로운 모델 플러그인 규격은 아니다.

- `ModelManifest.validate()`는 30Hz, 180시점, 32특징과 현 featureVersion을 요구한다.
- Python 학습 코드는 클래스 목록, `Dense(5)`, `[1,5]` 출력 검사를 고정하고 있다.
- Android 런타임은 입력 하나·출력 하나와 float32를 요구한다.
- 진행률 설정은 모든 운동이 공유한다.

같은 입력과 softmax 출력을 유지하는 분류기 교체는 비교적 작게 수행할 수 있다. 단계 출력, 상태를 가진 GRU, 그래프 입력, INT8 입력/출력을 도입하려면 manifest·전처리·출력 해석·런타임을 함께 변경해야 한다. 내부 가중치만 양자화하고 float32 입출력을 유지하는 방식과 완전 정수 입출력 방식은 구분한다.

다음 버전에는 모델 ID/버전, 입력 특징 규격, 출력 종류·이름·shape·dtype, 지원 운동, 포즈 모델 호환 조건을 명시한다. SDK·전처리·모델을 함께 버전 관리하고, 구버전 번들 호환성 또는 명확한 거부 동작을 검증한다.

새 운동을 추가할 때는 데이터·클래스·단계 정의·평가 기준까지 묶은 운동 팩으로 관리한다. 예를 들어 런지는 좌우를 각각 셀지 한 쌍을 셀지, 플랭크는 반복 수 대신 유지 시간을 반환할지부터 정해야 한다.

**5. 데이터와 평가 개선**

현재 참가자별 분리와 학습 참가자로만 계산한 정규화 통계는 유지한다. 다만 최소 3명은 파이프라인 실행 조건이며 실사용 성능의 근거가 아니다.

`valid:false`인 반복 전체를 `other`로 만드는 현재 정책은 운동 종류와 완성도·품질을 섞는다. 중단한 스쿼트의 초기 움직임은 완성한 스쿼트와 같을 수 있으므로, 온라인 모델에 불필요한 모순을 줄 수 있다. 운동 종류, 반복 완료 여부, 단계, 관측 품질을 구분해 라벨링하는 방향을 검토한다.

수집에는 연속 세트, 빠른/느린 속도, 바닥 정지, 부분 반복, 동작 중단, 의자에 앉기, 물건 줍기, 걷기, 운동 전환, 짧은 가림을 포함한다. 같은 운동만 촬영한 짧은 파일 외에 대기·전환이 섞인 긴 세션을 시험에 포함한다. 참가자 외에 촬영 세션·기기·카메라 각도·포즈 모델 메타데이터도 기록한다.

현재 로더는 전체 시계열 창을 메모리에 보관한다. 5Hz 학습 샘플, 180×33 float32 기준으로 1시간당 입력 배열만 약 428MB이며, Python 객체와 변환 중 복사본은 별도다. 수집 규모가 커지면 원시 특징을 저장하고 창을 배치 단위로 생성하는 로더로 바꾼다.

[evaluate.py](../training/motion_training/evaluate.py)는 이미 반복 누락·오검출·인식 지연·진행률 평가 가능 비율을 계산한다. 다음 보완을 권장한다.

- 운동·사람·속도·촬영 조건별 반복 precision/recall, 세트 단위 오차, 대기 시간당 오카운트, 완료 확인 지연의 p50/p95를 보고한다.
- 현재 종료 시각 -300ms~+1500ms 범위의 이벤트 매칭 외에 반복 시작/종료 시각과 ID를 활용해 인접 반복 오매칭을 줄인다.
- 단계가 검출된 경우만 계산하는 경계 MAE에 단계 누락률을 함께 제공한다. 인접 반복의 같은 단계가 재사용되지 않도록 구간별로 매칭한다.
- 완료한 실제 시각과 이벤트 발행 시각을 분리하여 동작 경계 오차와 확인 지연을 구분한다.
- 시간에 따른 선형 보간 진행률은 정지·비선형 속도를 정확히 나타내지 못하는 근사치다. 이 수치를 단독 최적화 목표로 삼지 않는다.
- 릴리스 기준은 목표 제품에 맞춰 미리 정하고, 동일한 시험 세트로 반복 조정하지 않는다.

**6. 외부 앱용 SDK 개선**

기본 모델 로딩, 직렬 실행과 수명 관리, 오류·관절 품질 안내를 SDK의 선택적 편의 계층으로 제공한다. 현재처럼 `PoseFrame`을 직접 넣는 저수준 API도 유지하면 자체 카메라·포즈 파이프라인이 있는 앱과 통합하기 쉽다.

결과에는 운동별 누적 횟수, 반복 이벤트 ID, 현재 단계, 관측 품질과 거부 사유를 제공한다. 운동 분류 점수와 포즈 품질, 반복 확신도는 의미가 다르므로 별도 필드로 둔다. 점수를 보정하지 않았다면 확률로 표시하지 않는다.

성능 최적화는 전체 경로 프로파일링 후 수행한다. 샘플의 매 프레임 Bitmap 생성·회전과 파일 기록, 코어의 시계열 배열 복사, 모델 추론의 비중을 먼저 측정한다. 분류 실행 빈도와 기하 추적 빈도를 분리하는 실험은 가능하지만, 분류 근거의 시각·유효 기간과 카운트 지연을 함께 검증한다. 수집 시각은 처리 시작 시각보다 카메라 프레임 타임스탬프를 단일 기준으로 변환해 사용하는 방향이 적합하다.

배포 검증에는 같은 저장소의 `project()` 의존성뿐 아니라 별도 앱이 Maven 아티팩트와 기본 모델만 받아 사용하는 경로를 포함한다. release/R8 빌드, 최소 지원 Android, 앱 중단·복귀·모델 교체를 확인한다. iOS는 현재 런타임이 없으므로 별도 플랫폼 작업이다.

**7. 권장 실행 순서와 완료 기준**

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 위 재현 사례를 회귀 테스트로 추가하고 카운팅 수정 | `other` 전환·유실·연속 반복의 명시된 정책 충족, 점프 중복 집계 방지 유지 |
| 2 | 스쿼트 지정 모드, 품질·이벤트 API, 운동별 설정 | 학습 모델 없이도 제한된 조건의 카운팅을 독립 검증 가능 |
| 3 | 실제 데이터 수집, 현재 TCN 학습, 반복 평가 | 보지 않은 사람·실기기에서 사전 정의한 기준 충족 |
| 4 | 단계 예측 TCN, 관절 품질/특징 개선 실험 | 동일한 검증 조건에서 기준 모델 대비 누락·오검출·지연 개선 |
| 5 | 운동 팩, SDK 기본 모델, 외부 앱 배포 | 별도 앱 release 빌드와 장시간 사용 검증 통과 |
| 이후 | ST-GCN·GRU·범용 반복 모델 비교 | 구체적으로 확인된 실패 유형에서 추가 복잡성의 이점 입증 |

**검증 범위**

- Python 기존 테스트 7개 통과.
- `./gradlew :core:jvmTest --rerun-tasks --console=plain`으로 JVM 기존 테스트 15개를 재실행해 모두 통과했다. 위 경계 시나리오는 별도의 임시 Java 프로브에서 빌드된 Kotlin 코어를 직접 호출했다.
- 카운팅 프로브는 동일 좌표의 분류/유실 조건과 반복 간 상단 유지 시간만 바꿔 비교했다.
- 모델 후보의 논문·공식 문서는 설계 참고용으로 확인했다. 실제 데이터 학습, 새 모델 변환, 실기기 정확도·성능 비교는 이번 분석에서 수행하지 않았다.
